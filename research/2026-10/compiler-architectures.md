## 1. CompCert
- Pipeline [K, Leroy CACM 2009 / JAR 2009; compcert.org docs]: C source → (OCaml, unverified) preprocessor (external cpp) + parser + elaborator (`cparser/`, CompCert C AST; the Menhir parser has a validated LR(1) automaton, Jourdan–Pottier–Leroy ESOP 2012) → **CompCert C** → SimplExpr → **Clight** → SimplLocals → **Csharpminor** → Cminorgen → **Cminor** → Selection → **CminorSel** → RTLgen → **RTL** (optimisations: Tailcall, Inlining, Renumber, Constprop, CSE, Deadcode, Unusedglob; Allocation is register allocation *validated* by a verified checker, i.e. translation validation of an OCaml IRC allocator) → **LTL** → Tunneling → Linearize (+CleanupLabels, Debugvar) → **Linear** → Stacking → **Mach** → Asmgen → **Asm** (per arch: x86-32/64, ARM, AArch64, PowerPC, RISC-V). Back-end compiled to text by the **asm printer (OCaml, trusted)**, then the external **assembler + linker (trusted)**.
- Theorem: a backward simulation / behavior refinement. If the source program has no undefined behavior *in CompCert C semantics* ("does not go wrong"), every behavior of the Asm program is a behavior of the source (traces of I/O events, termination/divergence). Separate-compilation correctness came later (Kang et al. POPL 2016 "Lightweight verification of separate compilation"; CompCert ≥3.0 supports it). [K]
- Semantics/UB [K]: CompCert C fixes many implementation-defined choices (sizes, two's complement). **Signed integer overflow wraps** (Int.add etc.; defined, unlike ISO C). Uninitialized reads give `Vundef`, and branching on or dereferencing `Vundef` is UB. Pointer arithmetic is block/offset based, so out-of-bounds access is UB and pointer comparisons are restricted. Division by 0 and INT_MIN/-1 are UB. Shifts ≥ width are UB. Volatile accesses are observable events. External calls are events. The memory model is v2 (Leroy–Appel–Blazy–Stewart 2012). There is no strict-aliasing UB in the TBAA sense, because type punning through memory goes via memory-chunk semantics. The reference interpreter `ccomp -interp` can detect UB along one execution.
- TCB [K]: Coq/Rocq kernel; **extraction** to OCaml; the OCaml compiler and runtime; the unverified frontend (cpp, elaboration of C to CompCert C: struct layout, bitfields, initialisers, etc.); the hand-written OCaml helpers (register allocator *output* is validated, so it is not in the TCB; the IRC heuristic is fine); the **asm printer** (`TargetPrinter.ml`); the external **assembler and linker**; runtime library/startup; the formal specs (C semantics, Asm semantics as a model of the real ISA). Testing: Yang et al. PLDI 2011 (Csmith) found bugs only in the unverified parts (frontend and the then-unverified parts).
- **Valex** (AbsInt, commercial): a translation validator that checks the linked executable against CompCert's Asm. It disassembles and compares, which removes the printer/assembler/linker from the trusted path for qualification (Kästner et al., ERTS 2018 "CompCert: Practical experience on integrating and qualifying a formally verified optimizing compiler"). [K]
- **CompCertELF** (Wang, Xu, Wilke, Shao, OOPSLA 2020): a verified assembler to relocatable ELF plus verified separate compilation and linking. Follow-up APLAS 2023 "Towards a framework for developing verified assemblers for the ELF format" uses CSLED to generate verified encoders/decoders for full x86 and RISC-V in CompCert. [V]
- **CompCert-CT**: Barthe, Blazy, Grégoire, Hutin, Laporte, Pichardie, Trieu, "Formal verification of a constant-time preserving C compiler", POPL 2020, DOI 10.1145/3371075, ePrint 2019/926. It modifies CompCert to remove leaking transformations, instruments every IL semantics with leakage (branches and memory addresses), and proves CT preservation through the whole pipeline. The proof technique is "CT-simulations" (lockstep-ish simulation diagrams over pairs of executions). **Availability:** it is a research artifact on an older CompCert (3.x around 2019). It is **not upstreamed** into compcert.org or AbsInt CompCert. I found no maintained public repo (the Dagstuhl artifact "knothed/CompCert-ct" is a different, later project). [V for paper / ? for code]
- **Licensing** [V]: INRIA Non-Commercial License (education/research/evaluation only). Some files (lib/, common/, export/, parts of cfrontend/backend/cparser/extraction) are dual-licensed LGPL-2.1+. Commercial use requires an AbsInt Software Usage Agreement. Consequence: shipping a commercial product that requires users to run CompCert needs an AbsInt licence. Using CompCert's *semantics* in proofs (e.g. via a Rocq model) is a different matter from distributing the compiler.

## 2. CakeML [K]
- Kumar, Myreen, Norrish, Owens POPL 2014. New backend: Tan, Myreen, Kumar, Fox, Owens, Norrish ICFP 2016 / JFP 2019 "The verified CakeML compiler backend". HOL4. Source is an SML-like language. About 12 ILs (flatLang, closLang, BVL, BVI, dataLang, wordLang, stackLang, labLang, then target machine code). Targets: x86-64, ARMv6/ARMv8, RISC-V, MIPS-64, Silver (a verified CPU). ISA models come from L3 (Fox). Verified GC, verified bignums, and a verified **instruction encoder to bytes**.
- **Bootstrapped in logic**: the compiler is evaluated *inside HOL4* on its own source (proof-producing evaluation, cv_compute/EVAL). This yields a verified machine-code compiler binary, with no extraction and no unverified host-language compiler. That is the answer to Thompson's problem.
- **FFI oracle model**: the semantics is parameterised by an oracle `ffi_state` for foreign calls. The correctness theorem holds *assuming* the real FFI C functions (basis_ffi.c) behave as the oracle and respect the memory interface (only touching the passed byte array). The basis library proves I/O specs against a model of the file system/stdin/out (Characteristic Formulae, Guéneau, Myreen, Kumar, Norrish ESOP 2017).
- Trusted: the HOL4 kernel (and Candle, a verified HOL Light implementation in CakeML, now exists: Abrahamsson et al. ITP 2022); L3 ISA models; the hand-written startup/FFI glue C plus the system C compiler/linker *for the glue only*; the OS/loader; the encoding of output bytes as `.byte` directives in a `.S` file (trivial printer). It also assumes enough memory: out-of-memory is a permitted "early exit" behavior.
- Spin-offs: **Pancake** (a verified low-level systems language reusing the CakeML backend; Pohjola et al. "Pancake: Verified systems programming made sweeter", PLOS 2023). Brack (verified Scheme via CakeML, CPP 2026). [V for Brack]
- CakeML gives *functional* correctness down to bytes. It has **no CT/leakage-preservation** theorem (there is space-cost work: Gómez-Londoño et al. "Do you have space for dessert?" PLDI 2020).

## 3. Jasmin [K + V]
- Almeida, Barbosa, Barthe, Blot, Grégoire, Laporte, Oliveira, Pacheco, Schmidt, Strub, CCS 2017 "Jasmin: High-assurance and high-speed cryptography". Coq. Source is a "high-level assembly": explicit register/stack/reg-ptr annotations, `inline` functions, `for` loops unrolled at compile time, `while`, arrays, and direct use of target instructions (intrinsics). Targets: x86-64 (with AVX2), ARMv7-M (Cortex-M4), RISC-V (RV32IM).
- Passes (Coq, extracted to OCaml): typing/pretyping (OCaml, trusted), inlining, unrolling, constant propagation, dead code elimination, array expansion/register arrays, **stack allocation** (OCaml oracle + Coq checker), **register allocation** (OCaml + verified validator, i.e. translation validation), lowering (to target-specific ops, flags), tunnelling, **linearization**, asm generation into a Coq Asm model, then the **OCaml asm printer (trusted)** to GAS syntax, then the external assembler (trusted).
- Proofs: functional correctness (CCS 2017). **CT preservation** via structured leakage and leakage transformers: Barthe, Grégoire, Laporte, Priya, "Structured leakage and applications to cryptographic constant-time and cost", CCS 2021. Earlier ad hoc version: "The last mile", S&P 2020 (Almeida et al.). **SCT (Spectre v1)**: Arranz Olmos, Barthe, Blatter, Grégoire, Laporte, "Preservation of speculative constant-time by compilation", POPL 2025, DOI 10.1145/3704880, ePrint 2024/1203. Negative result: GCC -O0/-O1 and the *actual* Jasmin compiler both break SCT on secure programs. Positive result: a PoC compiler keeping Jasmin's critical passes is proved SCT-preserving in Coq. They fix this by patching the SCT type checker (Shivakumar et al. S&P 2023 "Typing high-speed cryptography against Spectre v1"). [V]
- How it avoids C: the source is already near-assembly, so there is no undefined behavior to inherit and no optimiser that reintroduces branches. The predictability of the output is a design goal ("assembly in the head"). The libjade/formosa-crypto ecosystem uses EasyCrypt for proofs of Jasmin source (ML-KEM: Almeida et al. CRYPTO 2024).
- Trust: Coq kernel, extraction + OCaml, frontend, **asm printer**, assembler/linker, ABI/startup, and the Asm semantics as an ISA model (x86 semantics for many instructions is hand-written in Coq).

## 4. Cogent (UNSW / Trustworthy Systems) [K]
- O'Connor et al. ICFP 2016 "Refinement through restraint: bringing down the cost of verification"; Amani et al. ASPLOS 2016 (BilbyFs, ext2); Rizkallah et al. ITP 2016 "A framework for the automatic formal verification of refinement from Cogent to C"; O'Connor et al. JFP 2021 "Cogent: uniqueness types and certifying compilation". The source is a linear/uniqueness-typed total functional language with an abstract-type FFI to hand-written C.
- **Certifying compilation**: the Haskell compiler emits C, **plus** an Isabelle/HOL shallow embedding, **plus** Isabelle proof scripts per compiled program. Chain (bottom-up): C → **Simpl** (deep embedding, via the seL4 **C parser** of Tuch/Norrish, trusted, StrictC subset) → **AutoCorres** monadic embedding (proof-producing, AutoCorres proves its own step) → Cogent **update semantics** (deep, imperative, with mutable heap) → **value semantics** (pure; justified by the uniqueness type system, proved once generically) → monomorphic → polymorphic deep → **shallow HOL embedding** (where users do functional proofs). Key metatheorem: *well-typed linear programs satisfy update ⇒ value refinement*. This is proved once. The per-program step is tactic-generated.
- Trusted: Isabelle kernel; **C parser semantics** (C → Simpl) plus the StrictC assumptions; the **C compiler** (gcc) unless binary validation is added; abstract-function C code plus its stated specs (the FFI assumptions); and **certificate completeness**, meaning tactics may fail (that is incompleteness, not unsoundness). Not trusted: the Cogent compiler itself.
- Lesson for this project: a per-run, checked certificate is a good fit for a solo project. The generic metatheory is proved once, and each compilation emits a cheap proof object. Status: active development has largely tapered since about 2022 [?].

## 5. Low*/KaRaMeL, Vale, HACL* [K]
- **Low***: Protzenko et al. ICFP 2017 "Verified low-level programming embedded in F*". A shallowly embedded subset of F* with a memory model (HyperStack/LowStar.Buffer) is translated to **C*** and then C. The Low*→C* translation (λow* → C*) correctness and *side-channel* (trace-equivalence) preservation are proved **on paper**. **KaRaMeL** (formerly KreMLin) is an unverified OCaml tool and is **trusted**. F* extraction is trusted, and the F*/Z3 TCB is huge (SMT plus F*'s typechecker). The emitted C is compiled by gcc/clang/MSVC/CompCert, which are trusted. The C is designed to be UB-free (no signed overflow: machine ints are unsigned with explicit wrap; overflow checks for signed).
- **Secret integers** (HACL*: Zinzindohoué et al. CCS 2017): an abstract type `uint_t SEC` lacks branching/comparison/division, so CT holds at source, then *relies on the C compiler not to introduce secret branches/memory accesses*. HACL* is tested with CompCert too, and the CT reasoning stops at C.
- **Vale**: Bond et al. USENIX Sec 2017 (Dafny); Fromherz et al. POPL 2019 "A verified, efficient embedding of a verifiable assembly language" (Vale in F*). It verifies assembly directly against an x64 semantics in F*, including taint analysis for CT ("leakage-free" checker verified in F*). Trusted: the x64 semantics model, the **asm printer** (Vale's printer to GAS/MASM), and the assembler.
- **EverCrypt** (Protzenko et al. S&P 2020) combines HACL* C plus Vale asm with a verified agile/multiplexing API. Interop between C and Vale assembly goes through a verified calling-convention model (Fromherz et al.).
- Lesson: C as a *trusted extraction target* plus hand-proved translation is the industrial path. The CT guarantee ends at C unless the C compiler preserves it (CompCert-CT) or the binary is checked.

## 6. seL4 binary verification [K + V]
- Sewell, Myreen, Klein, PLDI 2013 "Translation validation for a verified OS kernel". seL4 C goes through **gcc -O1/-O2** to ARMv7 binary. The binary is **decompiled into logic** (Myreen's proof-producing decompiler, HOL4, using the Cambridge ARM L3/HOL4 ISA model). The C side uses the C parser's semantics. Both are converted to a common graph language, and **graph-refine** (Python, SMT: Z3/SONOLAR/CVC4) discovers and checks the refinement between them (loop-relation inference, stack/calling-convention handling).
- RISC-V 64 binary verification announced 2021 (HENSOLDT/Data61; Brecknell, Kocsis et al.). The 2025 seL4 Summit slides describe the newer "SydTV-GL" translation validation chain. [V]
- Removes gcc from the TCB. **Trusted**: the ISA model (L3 ARM/SRI RISC-V Sail-derived), the decompiler for the HOL4 part (proof-producing, so low trust), **graph-refine and the SMT solvers** (results are not all reconstructed as kernel proofs; this is the weak link), C-parser semantics, and some assumptions (stack layout, handwritten asm and boot code excluded).
- Lesson for this project: **post-hoc translation validation of an untrusted optimiser** is feasible when the compiled program has simple structure. It is easier still when you control the source compiler and can emit hints (block correspondence, loop invariants).

## 7. LLVM IR / Vellvm; WebAssembly / WasmCert / CT-Wasm [K]
- **Vellvm**: Zhao, Nagarakatte, Martin, Zdancewic POPL 2012 (original). Rewritten as Zakowski et al. ICFP 2021 "Modular, compositional, and executable formal semantics for LLVM IR" (interaction trees, Coq), with ongoing memory-model work (Beck et al. 2024 "Two approaches to LLVM's memory model / infinite & finite memory" ICFP 2024 [?]). It gives a semantics and some verified optimisations, but **no verified LLVM backend**, so llc is fully trusted. Related: Alive2 (Lopes et al. PLDI 2021) is translation validation of LLVM opts (bounded, SMT), and Crellvm (Kang et al. PLDI 2018) produces checked proofs for some passes. **LLVM actively breaks CT** (Simon, Chisnall, Anderson EuroS&P 2018 "What you get is what you C"; Schneider et al. 2025 "Breaking Bad" arXiv 2410.13489, 44,604 targets; Geimer & Maurice 2025 "Fun with flags" arXiv 2507.06112, a few passes cause most leaks). Dead-store elimination removes secret zeroization (Yang et al. USENIX Sec 2017). [V for Breaking Bad/Fun with flags]
- **WebAssembly**: the spec has an official formal semantics (Haas et al. PLDI 2017). Mechanisations: WasmCert-Isabelle (Watt CPP 2018, soundness, found spec bugs), WasmCert-Coq (Watt et al. FM 2021 "Two mechanisations of WebAssembly 1.0"; verified interpreter), Iris-Wasm (Rao et al. PLDI 2023, separation logic). Verified sandboxing compilers: **vWasm** (F*, proved sandbox-safe; Bosamiya et al. USENIX Sec 2022) and rWasm (Rust, not verified, uses Rust safety). VeriWasm (Johnson et al. NDSS 2021) checks Lucet output. Cranelift ISLE rules verified (Crocus, ASPLOS 2024).
- **CT-Wasm**: Watt, Renner, Popescu, Lerner, Stefan, POPL 2019. It adds secret types (`s32`/`s64`) and a type system proving CT, mechanised in Isabelle, with a V8/SpiderMonkey prototype. It is not standardised, and the JIT engine is trusted to preserve CT, which nothing proves.
- Assessment: Wasm gives a clean, small, mechanised target semantics and **memory safety/isolation by construction**. But the runtime (wasmtime/V8 JIT) is a huge TCB, and CT is not preserved by any production engine. LLVM IR gives semantics only (and Vellvm is not in Lean); the backend is fully trusted and adversarial for CT.

## 8. Lean 4's own compiler
- Pipeline [V/K]: Elaborated `Expr` → LCNF (base → mono → impure phase, since 4.29) → (being merged) IR → **EmitC** → C → bundled clang → link against the Lean runtime (C/C++: RC, `lean.h`, GMP or in-house bignums, Tasks, IO).
- Not verified at all. `@[implemented_by]`, `@[extern]`, `unsafe`, `partial` and `noncomputable` break the link between the logical definition and the executed code. `implemented_by` can make runtime behavior differ arbitrarily from the proven definition. Compiler bugs have occurred (miscompilations tracked on GitHub). Since 4.35 the *kernel* is fully compiler-independent (no trustCompiler, and native_decide uses explicit per-computation axioms that `lake check` rejects), but **executing** a Lean-compiled binary trusts LCNF+IR+EmitC+clang+runtime. That is roughly 100k+ lines plus LLVM.
- Implication: "compile via Lean" gives an executable whose correctness w.r.t. your Lean semantics is *unproved*. CT is hopeless: boxed values, RC, allocation, and branches on tags.
- **The trick that avoids trusting it**: run the certified compiler **inside the kernel**. Prove a theorem `compile src = bytes` (or `check src out cert = true`) by `decide`/`rfl` with `bytes` as a literal, or better, prove `checker ... = true` by `decide` where the checker is proved sound. The trust then reduces to kernel reduction (GMP-accelerated Nat, String/ByteArray literals). `lake check` and lean4lean/external checkers can then re-check the proof. This is the Lean analogue of CakeML's in-logic bootstrap. Cost: kernel evaluation is slow (whnf, no compilation), so it is practical for small programs or with efficient structural recursion (avoid well-founded recursion; use fuel/structural recursion so `decide` reduces). Getting the bytes out of Lean then needs only a trivial printer, whose output is checked by re-reading the file and comparing in the kernel (or via `#guard`-style kernel-checked equality on the file contents read at elaboration time; that read uses IO, so keep the comparison step itself kernel-checked).

## 9. Emitting C safely
- ISO C UB relevant to codegen [K]: signed overflow; shifts by ≥ width or negative; INT_MIN/-1 and /0; reading an uninitialized automatic object (UB if the address is never taken / indeterminate value; C11 6.3.2.1p2); strict aliasing (6.5p7); unsequenced side effects (6.5p2); out-of-bounds pointer arithmetic (even forming the pointer); null/misaligned deref; side-effect-free infinite loops with non-constant controlling expression may be assumed to terminate (C11 6.8.5p6); data races; overlapping memcpy; `restrict` misuse; and lossy conversions to signed type, which are *implementation-defined*, not UB.
- Codegen discipline ("defensive C subset", à la KaRaMeL/Cogent/StrictC): only `uint8_t..uint64_t` arithmetic (wrap is defined); signed values derived via explicit two's-complement helpers; masked shift amounts (`x << (s & 63)`); division only through a guarded helper; all locals initialised at declaration; one side effect per statement (A-normal form) so sequence points are moot; no pointer casts, no unions for punning (use `memcpy`), arrays as `uint8_t[]` with statically-proved in-bounds indices; no recursion beyond a proved stack bound; loops always have a fuel or observable effect. Add `-fwrapv -fno-strict-aliasing -fno-delete-null-pointer-checks` as belt-and-braces, *not* as the argument.
- Checking tools: **Cerberus** (Memarian et al. PLDI 2016, POPL 2019 provenance; executable ISO semantics, detects UB on tests), **CN** (Pulte et al. POPL 2023; refinement-type/separation-logic verification of C, used on pKVM), **Frama-C** RTE plugin (generates ACSL assertions for every potential UB) + WP/EVA to discharge them, **CompCert interpreter** (`ccomp -interp`, CompCert-UB on one run), and VST (Appel et al., Coq separation logic over CompCert Clight; strongest, the proof connects to CompCert's theorem).
- Integer representation: the source must commit to **fixed-width modular** (u64) or **checked fixed-width** semantics. Unbounded `Int`/`Nat` (Lean's) would require a bignum runtime: big TCB, variable-time, allocation. For security certificates (cost/CT) unbounded ints are disqualifying because their timing depends on the value. Recommend: source language integers are `BitVec 64` (Lean core has `BitVec`, with bv_decide), and the cost model counts per-op constant cost.
- Why UB-free is not enough for security: compilers are only obligated to preserve *I/O-observable behavior*. Timing, memory-access pattern, branches, residual secrets in dead stores, and register/stack spills of secrets are not observable in the C abstract machine, so optimisations may legally change them. Examples: select → branch, `cmov` → jump, bitmask tricks recognised and turned into branches; loop early-exit introduced; memset zeroization removed; secret-indexed table lookups introduced by switch lowering; variable-time `div`. Hence CT/NI-on-traces needs either a leakage-preserving compiler (CompCert-CT, Jasmin) or **binary-level checking** (e.g. a CT checker on the final asm: Binsec/Rel (Daniel et al. S&P 2020), ct-verif (Almeida et al. USENIX Sec 2016, on LLVM IR, so not binary), or your own checker on your own asm model).

## 10. Trusted printers/assemblers, DDC, bootstrapping
- The printer/assembler/linker is in the TCB of CompCert, Jasmin, Vale, and Cogent+gcc. Removals: Valex (AbsInt, validation), CompCertELF/CSLED (verified encoders), CakeML (verified encoder to bytes in logic), and seL4 TV (decompile the final binary, which covers the assembler and linker too since the *linked image* is checked).
- **Diverse Double-Compiling**: Wheeler ACSAC 2005 / PhD 2009. It counters Thompson's "trusting trust" (CACM 1984) by recompiling a compiler's source with a diverse trusted compiler and checking bit-for-bit equality of stage-2 outputs. It needs reproducible builds. Bootstrappable builds: GNU Mes / stage0 (hex0 seed of a few hundred bytes), Guix full-source bootstrap (2023). For this project the Lean toolchain binary itself is the hard root. Mitigations: lean4lean (in-Lean kernel), external checkers in the 4.35 toolchain, and `lake check` / comparator re-checking.
- **Verified ISA models in Lean** (an important enabler): the **Sail → Lean backend** now generates the official sail-riscv model as Lean (SailM monad), used by SP1 Lean verification work. **LNSym** (AWS, Lean 4, AArch64 ISA model plus symbolic simulator, conformance-tested against hardware; used in AWS-LC AArch64 crypto proofs). So a RISC-V (or AArch64) target semantics in Lean exists and need not be hand-written. [V]

## 11. Ranking for this project (solo, Lean 4, bulletproof > perf)
Properties to carry: NI, CT (trace/cost), memory safety, mediation, injection-freedom. Note that mediation, injection-freedom and memory safety are *trace/safety properties of I/O behavior*. Any behavior-refining compiler preserves them, because they hold for all source behaviors and refinement means target behaviors ⊆ source behaviors. **NI and CT are hyperproperties** and are **not** preserved by plain refinement (refinement can reduce nondeterminism in leaky ways, and observability changes at lower levels). They need leakage-aware simulations ("CT-simulation", 2-safety preserving, Barthe et al. CSF 2018 "Secure compilation of side-channel countermeasures: the case of cryptographic constant-time").

## 12. Staged path (concrete)
Stage 0 (now, days): **Reference interpreter in Lean** plus a `lake exe` that runs it. Label it "UNCERTIFIED EXECUTION: trusts Lean compiler". Purpose: testing oracle only. Also emit **UB-free C** (Option D) via a Lean pretty-printer, with differential testing interpreter-vs-C (Csmith-style random programs from your own generator). Record the TCB honestly: certificates hold at source only.

Stage 1 (weeks): **Fix target**: RISC-V RV64IM (rv32 is fine too). Reasons: an official Sail model is available as Lean, the ISA is small, there is no flags register, and every instruction is fixed-length (a trivial encoder) with no variable-time instructions except div/mul on some cores (forbid div on secrets; treat mul as CT only after a µarch check, or forbid it too). Alternatively AArch64 via LNSym. Import/pin the generated Lean model (track its commit hash in the TCB record). Write a *small* abstraction of it (a Lean `Asm` semantics) and **prove the abstraction against Sail-Lean** for the instructions you use. This removes trust in your own ISA model.

Stage 2 (months): **Verified Lean compiler** source → stack/register IR → RISC-V `Asm` (no optimisations: naive register allocation via stack slots, no CSE). Prove **behavior refinement** (gives memory safety, mediation, injection-freedom, functional correctness) and a **leakage-preserving lockstep simulation** (gives CT/NI). Lockstep plus a deterministic leakage transformer (Barthe et al. CCS 2021 "structured leakage") is the cheapest form. A non-optimising compiler makes leakage transformation a simple function of source leakage. Keep all recursion structural so the compiler **reduces in the kernel**.

Stage 3: **Verified encoder** `Asm → List UInt8` (RISC-V: easy; prove `decode ∘ encode = id` against the Sail decoder) plus a minimal ELF writer (static, no relocations, one PT_LOAD), plus a syscall shim written *in your Asm* (no libc). Run `compile src` **in the kernel** (`decide`/`rfl`) to get a theorem about the exact byte string. Write the bytes with a dumb IO printer, then re-read and compare in a kernel-checked step (or check the hash of the file externally against a hash the kernel computed). `lake check` (4.35) plus external checkers re-verify. TCB at this point: Lean kernel (multiple independent checkers), Sail RISC-V spec (as Lean), ELF loader/kernel syscall semantics, and hardware conformance to ISA plus µarch timing assumptions (document: "no secret-dependent branch, address, or div").

Stage 4 (optional, for performance): admit an **untrusted optimiser** (your own, or gcc on the UB-free C) under **translation validation** (Option B). The Lean checker decompiles the produced RISC-V binary into the Asm model and checks refinement plus leakage equivalence against your verified non-optimised output or against source, using hints. Fall back to the Stage-3 binary when validation fails. Never trust gcc for CT. If gcc output fails CT validation, reject it.

Stage 5 (optional): a **CompCert/Clight emitter** for customers who need DO-178C-style qualified toolchains, with honest TCB notes (cross-prover gap, CompCert-CT not maintained, AbsInt licence). Low priority for "bulletproof".

Upgrade toolchain to Lean **4.35** for: removal of `Lean.trustCompiler`/`ofReduceBool`, `lake check` (rejects nonstandard axioms), and bundled external checkers. Pin the version in the TCB record.
