## Plan

On the user's word (2026-10-27): "The 3-checker limit is checked one change at a time, so
several small changes in a row can still rewrite every checker and that's fine but there should
be an agent to make sure the boundaries are not crossed but they can evolve".

**What a checker edit cannot do, mechanically.** It cannot weaken a frozen statement: the
comparator re-proves each soundness theorem against `tools/ring0.lock`. It cannot start refusing
an accept witness (the build fails), add an axiom (manifest), or touch Ring 0 (gate). Those stay
the authority.

**What the warden is for.** It covers what no rule states. Has a checker stopped checking what
its name and docstring say, while its soundness proof still holds? Has it grown so strict that
it refuses programs the witnesses do not cover? Is meaning being rebuilt on the checker side,
where the lock does not reach? Has cumulative drift taken a checker somewhere no single change
shows? Those are judgments, so an agent makes them. An agent is Ring 3 (CLAUDE.md): nothing it
says is believed except in the direction that costs nothing to believe. So the warden can only
**escalate**. `clear` grants nothing beyond the mechanical gate. `escalate`, or any answer that
does not parse, makes the change need the user's key.

1. **A baseline the user signs.** `tools/checkers.baseline` (Ring 0): `checkers.lock` as of the
   user's last sign-off, plus the commit it was taken at. `tools/ring0-lock.sh --baseline`
   writes it, with the user's key. The user re-baselines after reading a warden report; that is
   how the checkers evolve without the boundaries moving silently.
2. **The cumulative report** (`tools/gate/boundary-report.sh BASE_DIR PR_DIR`, mechanical):
   which checkers differ from the baseline, as of BASE and as of the PR. For each, the source
   diff of its modules since the baseline commit, and the docstring and soundness statement. It
   is the warden's only input, apart from read access to the PR tree.
3. **The warden** (`.claude/agents/boundary-warden.md`, prompt plus rules). It runs with
   read-only tools (`Read`, `Grep`, `Glob`) on the report and the PR tree. Its last line must be
   `WARDEN: clear` or `WARDEN: escalate`, with findings above it.
   `tools/gate/warden-verdict.sh` parses the output fail-closed: anything else is escalate.
4. **Where it runs.** A separate job in `gate.yml` that never executes PR code. It checks out
   both trees as data, runs the report and then `claude -p` with the warden. Only that job
   holds `ANTHROPIC_API_KEY`. It runs when the PR changes `tools/checkers.lock`. If the secret
   is absent, it reports ABSENT and fails, because CI never skips silently. Prompt injection
   from PR text can at worst produce `clear`, which grants nothing.
5. **Witnesses.**
   - The parser: clear, escalate, and a malformed verdict, which must count as escalate.
   - The agent, on two staged PR trees: an equivalent `costCheck` rewrite (expected clear), and
     a `costCheck` that returns `none` for everything except `skip`. That one is still sound,
     and the mechanical gate passes it if the witnesses allow; expected escalate.
   - The agent runs are real `claude -p` calls, through `tools/run-job.sh`, with their outputs
     committed as receipts.

Not covered: the warden is a model and can miss things; that is why it can only escalate. The
GitHub job needs the user to add the secret; until then the job reports ABSENT.
