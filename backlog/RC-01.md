## Plan

The user's decision of 2026-11-06: "we need to work on real code now", then, of three options, **"Real C, at the source"**: a front end that reads a
subset of real C into L's language and checks it there. L-BYTES' route is to grow `sliceLang`, so the subset grows the slice language, and
each construct goes through to the bytes.

**The first real code: libsodium's constant-time compare.** `src/libsodium/crypto_verify/verify.c` at tag `1.0.20-RELEASE`, sha256
`44642761…568ea9`, the portable (non-SSE2) `crypto_verify_n`:

```c
const volatile unsigned char *volatile x = (const volatile unsigned char *volatile) x_;   /* and y */
volatile uint_fast16_t d = 0U;
int i;
for (i = 0; i < n; i++) { d |= x[i] ^ y[i]; }
return (1 & ((d - 1) >> 8)) - 1;
```

with `crypto_verify_16` calling it at `n = 16`. Small, used everywhere, and security-critical: its whole point is that its time and memory
accesses do not depend on the secret bytes.

**The certificate is not `rel`.** The function returns whether the buffers are equal, so its result depends on the secret by design, and
`rel` refuses it. **Constant-time is `Cert.relView lowIn f`**, with an observer `f` blind to the result channel. Leakage, cost and outcome
must still be the same, at every fuel. The kernel has the shape and `relView_transfer`, so **no kernel change is expected.** The checker
needs a variant that does not require a public result.

**What the slice language lacks, each a step through to the bytes:**
- **Operators:** `^`, `|`, `&`, `-` and logical `>>` by a constant. `rvLang` gains `xor`, `or`, `sub` and `srli`, each compared with QEMU in
  `rv_diff.py`, with a broken model per instruction.
- **Byte arrays as inputs:** two read-only arrays of `n` bytes, the secret ones, in the data segment. Loads of bytes, which `rvLang` gains as
  `lbu`. Fixed length, so no aliasing and no bounds to check: the index is the loop's.
- **An increasing index:** `for (i = 0; i < N; i++)` with a literal `N` and `i` not assigned in the body, read as BOUND-01's counted loop,
  with `i = N - c`. Its budget is constant.

**The reading of C, a trust assumption stated once.** The front end gives each construct of the subset a meaning in L.
- `unsigned char` loads are zero-extended.
- `uint_fast16_t` is 64 bits, as on glibc for riscv64 and x86-64. This is a platform fact, and it is stated.
- `int` arithmetic on the values here stays in range, which needs a side check.
- `volatile` has no meaning in L. It exists to stop an optimising compiler. L's pipeline does not optimise, so it is read and dropped, and
  that is said.

The reading is believed **only by testing**: the original C, compiled by clang, and L's program run on the same inputs must agree.

**Steps, riskiest first.** Each ends with a report.
1. **The subset and its reading, on paper,** against the pinned source, before any parser.
2. **The operators, through to the bytes,** one at a time, with `rv_diff.py` cases.
3. **Byte arrays and the increasing loop,** through to the bytes.
4. **The constant-time checker,** with an accepted and a refused witness per rule, and `relView` on the source.
5. **The front end:** a parser for the subset, in Lean, so the reading is code that can be checked. It must take `verify.c`'s function as
   written, including `volatile` and the casts.
6. **`crypto_verify_16`, certified:** constant-time and a constant budget on its literal image, by transfer.
   - Under QEMU, on many inputs: traces and costs independent of the secret bytes.
   - Results equal to clang's compiled original, run natively.
   - **Teeth:** a variant with an early exit on the first difference (`if (x[i] != y[i]) return -1;`) is refused, and its bytes are seen to leak.
7. **The account,** including what of C is still out of reach.

## Log
- 2026-11-06, **step 1 done: the subset and its reading, on paper** ([`RC-01-READING`](../research/2026-11/RC-01-READING.md)), against the pinned source. The header is pinned too: `crypto_verify_16.h`, sha256 `d3b4fbea…44456c`, with `crypto_verify_16_BYTES` 16U.
  - **Every line is accounted for:** the branch (portable, as on RISC-V), the platform (LP64 and glibc, with widths measured on x86-64 and not on riscv64), the inlined call, the casts, `volatile`, the loop, the C11 promotions in `d |= x[i] ^ y[i]`, and the usual arithmetic conversions and implementation-defined `int` conversion in the return.
  - **`volatile` is not dropped silently.** The access-preservation it asks for holds of L's compilation by construction: every access once, in order, no optimisation. Whether clang's compilation keeps it is not claimed.
  - **The result is 0 exactly when the 16 bytes are equal, else -1**, the same on glibc and musl, though the leakage of a 32-bit `d` would differ.
  - **The subset is written down,** with what is refused: pointer arithmetic, writes through parameters, uncounted loops, unbounded `int`, signed shifts, division, other calls, `goto`, and preprocessor decisions.
  - **What L needs:** `^ | & - >>`, two read-only byte arrays with `lbu`, and an increasing index from `forN`. No kernel change is expected: the certificate is `relView`, locked.
- 2026-11-06, **step 2's design: two halves, the machine first.**
  - **2a, the machine:** `sub`, `xor`, `or`, `and` and `srli` in `rvLang`, each with its encoding, decoding and step. Each is compared with QEMU in `rv_diff.py`, with a broken model per instruction that the comparison must catch, and `Good` lemmas for the encoder.
  - **2b, the language:** `^ | & -` and `>> k` in the expression language VS-1 and VS-2 share, through `slotPass` and `rvPass`, keeping every existing proof and literal image.
- 2026-11-06, **step 2a done: the machine has the five instructions `crypto_verify_16` needs.**

Each has its encoding, decoding and step, and `W64.sub`, `xor`, `or` and `shr`. The decoder's new branches follow the existing ones, so every proof that reduced through `add`, `addi` and `andi` builds unchanged, and so do VS-1's and VS-2's literal images.

- 2026-11-07, **step 2b done: the operators in the language, through both passes to the bytes.**
  - **The language.** `Expr` and `SExpr` gain `.bin op a b`, for `sub`, `xor`, `or` and `and`, and `.shr a k`, a logical shift by a literal.
    - Their meaning is `Op.w`, the machine's (`Slice/Word.lean`). The lowering emits `opInsn op` and `srli`, and `okE` refuses a shift of 64 or more.
    - One lemma, `step_op`, gives the machine step for all four operators, so `genE_exec` has one new binary case and one shift case.
  - **Every existing proof, image and budget builds unchanged**, in VS-1, VS-2 and BOUND-01. Seven functions over expressions, outside the lowering, gained their cases.
  - **Witnesses** (`Slice2/Ops.lean`).
    - `verifyTail` is `crypto_verify_16`'s return expression over a public word. It is accepted, it means 0 for `d = 0` and the C `int` -1 for `d` from 1 to 255, and the compiled bytes agree.
    - Each operator with a secret operand is refused, and so is a shift of the secret. Each operator's value is shown on fixed operands.
    - A shift by 64 is refused, and one by 63 accepted.
  - **A finding, in the witness and not the code.** The expression is an equality test only on the range C gives `d`, which is an or of bytes, so at most 255. At `d = 2^64 - 1` it gives 0. The first draft of the witness claimed -1 there, and `decide` refused it.
  - **Mutants: 54 of 54 killed** (receipt `rc01-step2b-mutants`), 6 new. Five are killed where they should be: `step_op`, the operators' values, the noninterference proof, `genE_exec`, and `genE_good`. The sixth, `sub` emitted as `xor`, is killed in `good_op` by Lean's maximum recursion depth while it unifies the mismatched instructions. That is a refusal, but through a resource limit and not a clean type error.
  - **A footprint change for the user's key, found by comparing the manifest with `master`.** Four existing lines change from no axioms to `propext`: `LCore.Slice.eval`, `LCore.Slice.Slots.evalS`, and through them VS-2's `chunk` and `chunkC`. On `master` the machine's `step` already depended on `propext` the same way, through `W64.and` for VS-2's `andi`. `propext` is one of the three permitted axioms, not a new one. The manifest gate will refuse the merge until the user's key accepts it, which is what it is for.
    - **The alternative, not taken:** bit-by-bit `xor`, `or` and `and` defined structurally, without `Nat.bitwise`. That avoids `propext`, but duplicates the core definitions, and moving `W64.and` onto it would change the machine step's footprint too.

- 2026-11-08, **step 3's design, on the user's choice of "real arrays"** over unrolling the loop.
  - **No run function changes signature.** The slot language already holds the input words, in slots 0 to 63.
  - **The command, `loadB x names e`.** `x` receives byte `i` of the input words `names`, where `i` is `e`'s value masked to the array's length, which must be a power of two. It leaks `i`, as VS-2's array loads do.
    - In the source it reads the named inputs from the store. `names` must be consecutive inputs, like `[x0, x1]` for 16 bytes, so the slots pass maps them to consecutive slots.
    - On the machine: the index, `andi` with the mask, `add` the data base, `lbu`, and `sd` into `x`'s slot.
  - **The checker:** the index must be low, and `x` is high if any of `names` is.
  - **Three parts, riskiest first:**
    - 3a, `lbu` in `rvLang`, compared with QEMU, with broken models;
    - 3b, the command in the source, the slots pass and the checker, with `rel`;
    - 3c, the lowering through `rvPass`.
- 2026-11-08, **step 3a done: `lbu` in `rvLang`.** A byte, zero-extended, at `rs1 + imm`. It leaks its address and faults where the memory is not readable, as `ld` does.
