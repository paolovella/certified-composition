## Why

RC-01 step 5 states that `crypto_verify_16` is *read from libsodium's text*. Since 2026-11-08 the build checks two things, in `CSrc`'s
`#eval`:
- each vendored file hashes to its pinned sha256, by `Sha256`, which is self-tested;
- the excerpts the front end reads are the vendored file's lines.

Both pins live in ordinary files: the `PINS` list in `CSrc.lean`, and the copy in `third_party/libsodium-1.0.20/`. **An agent could change a
vendored file and its pin in one commit, CI would stay green, and the claim would quietly stop being true.** Only the user's key can close
this.

## Plan (for the key holder)

1. Add `third_party/` and the `PINS` list to `ring0.lock`, and to CLAUDE.md's Ring 0 list. The list may need to move to its own file, e.g.
   `third_party/PINS`, read by `CSrc`'s `#eval`, so the lock covers one whole file.
2. Write a witness: one byte of `verify.c` and its pin edited together. The base gate must refuse it.
3. Write the accepted witness: an edit outside `third_party/` passes the gate.

The agent does not do this. It proposes, and the user merges.

## Log
- 2026-11-08, **a second gap, found in RC-02 step 5: the pin check does not run on a cached build.** `CSrc`'s `#eval` hashes the vendored files when `CSrc.lean` is compiled, and Lake does not recompile it when only a vendored file changes.
  - Seen: with `utils.c` changed by one character, `lake build` passed from cache, and `lake env lean LCore/Slice2/CSrc.lean` failed.
  - **Proposed, for the user's key:** a CI step that runs `lake env lean LCore/Slice2/CSrc.lean` and requires it clean, or the vendored files declared as inputs of `CSrc` in `l-core`'s lakefile. Either one, with a refused witness that edits one vendored byte.
