# Where this actually stands, and what the breakthrough would have to be

*Written 2026-08-13, after stage 3a. Sources at the end. This document is deliberately
unflattering: it exists because the tests in this repo were rigged and the checker has
never been measured.*

---

## 1. The honest verdict on what we have

### 1.1 The tests are rigged

`examples/handler.uc` is `loopHandler` transcribed into text. I proved it checks, then
wrote the file that checks. The six files in `examples/rejected/` are the same trick
inverted: each was written knowing which rule would catch it. **No program in this repo
was written before the rule that certifies it.** That is not a test suite; it is a
demonstration reel.

### 1.2 The number nobody has measured

Every checker here is **sufficient, not necessary**, and the modules say so in six places:

| Rule | What it over-rejects |
|---|---|
| `slcheck` load rule | drops the loaded value from the tracked set — a loaded pointer can *never* be dereferenced |
| `medCheck` join | intersects, so a resource authorized on one branch only is refused |
| `needs` (stage 2c) | syntactic, so `access` in dead code is still charged |
| `jcheck` loop | exact fixpoint on the tracked set |
| `bcheck` (stage 2j) | recognizes **one** loop idiom: constant-initialised countdown |
| `interStr` at `ite` | tracked set is the intersection of both branches |

The false-rejection rate on programs a person would actually write is **unknown**. It has
never been estimated, and no corpus exists to estimate it on. For comparison, the field's
own numbers: general sound analyzers run **10–20% false alarms per basic C operation**,
and Astrée's celebrated zero-alarm results are obtained by *tuning the abstract domains to
one class of programs* (synchronous avionics control code) — not by being generally
precise. We have no reason to believe our rate is better and several reasons (the table
above) to expect it is far worse.

### 1.3 The language is not a language

`UCmd` has ten constructors. No functions or procedures. No arrays, no records, no
pointers-into-structures. Arithmetic is `+` on unbounded `Int`. Strings are `List UCh`
where `UCh` has two constructors, `ord` and `quote`. I/O is one `emit`. **You cannot write
a real handler in it**, which means the five certificates are guarantees about programs
nobody would write.

### 1.4 What is nevertheless real

Not nothing, and it matters for what follows:

- ~1100 machine-checked declarations, no `sorry`, standard three axioms, CI-gated, with a
  guard suite that is itself mutation-tested (17/17).
- A culture of recorded refutations: stage 2f found a live defect by attacking its own
  conjecture; stage 2g proved the obvious proof strategy *cannot* work; stage 1u, 1y, 2a
  are counterexamples to the repo's own rules.
- Two structurally unusual assets, discussed in §3.

## 2. The frontier, as it actually is

### 2.1 Deep verification of small, critical code — this is where the field wins

**seL4.** Functional correctness *down to the binary*, plus integrity and confidentiality,
on **8,830 lines of real C** — the actual kernel implementation, not a model. World's
first source-level information-flow proof for a general-purpose OS kernel. Stated
exclusions: **timing channels are explicitly out of scope** of the confidentiality proof
(addressed separately and later, in the time-protection work); DMA devices assumed benign;
compiler, assembly, hardware and boot code assumed correct.

**Jasmin + EasyCrypt.** This is the one that should sting, because it is *exactly* the
territory of our stages 2d–2i. Jasmin enforces **speculative constant-time** with a
*value-dependent information-flow type system* that tracks security levels **depending on
whether execution is mis-speculating**; it types programs protected by fence insertion,
index masking, speculative load hardening and *selective* SLH; there is a POPL 2025 result
on **preservation of speculative constant-time by compilation**; and an ASPLOS 2025 result
extending protection to Spectre-RSB and, per its title, all known Spectre variants. This
runs on high-speed cryptographic code that ships.

Our stage 2i proves that a certified program's *address trace* is a function of the Low
part of its input, on a toy language, with no compiler, at address granularity, one global
misprediction window, no nested speculation. **Jasmin is several years and one deployed
toolchain ahead on every axis of that comparison.**

**HACL\*/EverCrypt (F\*/Low\*)** ship verified crypto in Firefox and the Linux kernel.

### 2.2 Verified analysis and verified substrates

**Verasco** — a formally verified sound static analyzer for most of ISO C99 (including
IEEE-754 floats; no recursion, no dynamic allocation), integrated with CompCert so
soundness carries to compiled code. This is the direct ancestor of `bcheck_sound`, done
for real C a decade ago.

**CN** (POPL 2023) — separation-logic refinement types for **systems C**, built on the
**Cerberus** C semantics, verifying absence of undefined behaviour plus ownership and
functional specs; **Fulminate** (POPL 2025) makes the same specifications
runtime-testable, which is a serious answer to the adoption problem.

**Vellvm** — mechanized semantics for most of the sequential fragment of **LLVM IR 14**,
differential-tested against Clang (finding bugs in both). A real substrate exists.

### 2.3 Composition — the nearest thing to our own claim

Work on **secure composition of compilers** shows that composing two compilers preserving
two distinct properties preserves *roughly the intersection* of those properties, with
conditions for when passes may be reordered without losing security meaning; one case
study chains six passes preserving four properties. **Universal Composability has been
identified as robust subset-closed hyperproperty preservation.** And, importantly for us:
**no effective procedure is known for checking that a compilation chain meets secure
compilation requirements.**

### 2.4 The graveyard we are currently walking into

**Jif and FlowCaml — the two canonical IFC languages — were not adopted**, and the
literature is blunt about why: **annotation burden** (porting Java to Jif requires
significant effort; the programmer must adapt program design to the enforcement
mechanism), and **limited permissiveness, i.e. too many false positives**, singled out as
"a roadblock on the way to wider adoption". Fine-grained IFC that extends the language and
compiler is described as *thwarting adoption* by construction.

**We are building a new IFC language with a new checker and a new surface syntax.** That
is the failed path, and our checker is *stricter* than Jif on at least three rules.
Recent work has moved to *retrofitting* IFC into existing languages instead (Rust:
Carapace, Filament; Java-like: Co-Inflow) precisely because of this.

## 3. Where we stand — and the one thing that is ours

Per property, against the specialists:

| Property | Frontier | Us | Verdict |
|---|---|---|---|
| Memory safety, real C | CN, VST, Verasco | toy heap, 10-constructor language | **far behind** |
| Info-flow / NI | Jif, FlowCaml, Co-Inflow, Carapace | same ideas, toy language | **behind, and on the failed path** |
| Speculative CT | Jasmin (+ compiler preservation, all Spectre variants) | address trace, one window, no compiler | **far behind** |
| Cost / DoS | WCET tooling, Astrée | instrumented step count | **behind** |
| Injection | taint analysis everywhere | 2-character alphabet | **behind** |
| Whole-system | seL4 | — | **not comparable** |

There is no property on which we lead, and it is unlikely there ever will be by continuing
this way. What we have that the specialists do not:

**(A) A checked algebra for accumulating heterogeneous certificates.**
`GradedAction`/`Bridge`, with `Bridge.pair_comp_cert` proving that composing a bundled
bridge is **componentwise** — no interaction term, no side condition — so carrying *n*
guarantees costs *n* independent accumulations. Five instance families inhabit it
(Lipschitz, Hölder, Dobrushin over finite/measure kernels, quantum channels, cost
budgets). The secure-compilation literature composes *compilers* and gets *intersections*
of properties; this is a different and finer object: multiple guarantees riding one
composition law.

**(B) A trusted base computed from the artifact rather than fixed.** Stage 2c's `needs`
derives the assumption ledger from the program's syntax, with `no_access_no_reads` and
`unwritten_sink_untouched` proving omissions are *earned*; `pureProg_deployed_with_nothing`
gets all three deployment guarantees with an **empty** ledger. The SBOM-as-a-theorem
framing (`LedgerBridge`) — provenance accumulating by the same law as the guarantee — has
no analogue I could find in the literature above.

These two are narrow, defensible, and currently attached to a toy. **The toy is the
liability; the algebra is the asset.**

## 4. The strategic choice

Three coherent directions. Only one survives contact with §2.

**Option 1 — keep building the language.** Add functions, arrays, records; grow `UCmd`
toward something writable. *Rejected.* This is the Jif path with a decade less funding.
Even completed, it produces a language nobody writes code in, and every property remains
behind its specialist.

**Option 2 — go deep on one property to beat a specialist.** *Rejected.* Pick any row of
the table: the incumbent has a deployed toolchain, a compiler-preservation theorem, and
years of adversarial attention. This is not winnable and would not be believed if claimed.

**Option 3 — become the composition layer over artifacts other tools already certify.**
Stop generating certificates for a toy language; start *accumulating* certificates that
CN, Jasmin, Verasco, or a Rust IFC tool already produce for real code, and prove the
composition law and the assumption ledger for those. **This is the only direction where
the existing asset is the thing being extended, and where "nobody has done this" survives
the literature search** (§2.3: composing *compilers* yields intersections; there is no
checked algebra for accumulating *heterogeneous per-artifact certificates* with a computed
trusted base).

## 5. The plan

Each stage has a **falsifiable milestone** and a **kill criterion**. A stage that trips
its kill criterion ends the direction; that is what makes this a plan rather than a hope.

### Stage A — Measure the checker we have. *(2–3 sessions. Do this first, regardless.)*

Everything downstream depends on whether generated certificates can be had at tolerable
false-rejection rates. We have no data.

1. Build a corpus of **50–100 small programs written to a spec, not to the rules** — the
   right method is to write the spec first, generate programs from it (or transcribe from
   textbook/CWE examples), and only then run the checker.
2. Measure: acceptance rate; for each rejection, classify as *true* (the program really
   violates the property) or *false* (the rule is too coarse), and attribute it to a rule.
3. Publish the table in the repo, including the bad number.

- **Milestone:** a per-rule false-rejection table on a corpus not authored to pass.
- **Done, first pass** (`conf-typing/corpus/`): 30 tasks, **5 inexpressible (17%)**,
  25 expressible, 20 accepted, 3 correct refusals, **2 false (8%)**. After the stage-2k
  widening, **1 false (4%)**. Both false refusals were in one rule, the stage-2j counted
  loop. **The corpus was author-written, and that was the binding limitation** — the next
  corpus had to come from outside this repo.
- **Done, second pass** (`conf-typing/corpus/ext/`): 12 programs transcribed from CWE
  demonstrative examples — code neither written by this repo nor for it. **Detection: 6 of
  7** (use-after-free ×2, missing authorization, injection, unbounded loop ×2). **Precision:
  4 of 5 safe programs accepted.** Two results matter more than the rates:
  - **The miss is a scope hole, not a soundness bug.** CWE-401 (allocate, take the error
    path, never free) is **accepted**. The memory certificate covers use-after-free,
    double-free and wild dereference; *no certificate in this repo detects a leak*, and
    `VULN-COVERAGE.md` now says so instead of omitting it.
  - **The one false rejection is the fix CWE-835 tells developers to write** (`b12`):
    validate the rate up front, then loop. The counted-loop rule reads its bound off a
    **syntactic constant**, so it refuses a bound that is a *variable validated by a guard*.
    Twenty-five author-written programs never found this; twelve transcribed ones found it
    immediately. Fixing it means letting the bound be a variable a guard has validated —
    the first *value-dependent* rule here. **But that is Option 1 work on a frozen
    component** (see "What happens to the existing work"), so it is recorded as a known
    limitation rather than scheduled.
  - 20% on five programs is a *pointer, not a precision figure*; what the corpus bought is
    the identity of the failing rule, not a rate.
- **Kill criterion:** if false rejection exceeds ~50% and is concentrated in rules that
  cannot be relaxed without losing soundness, then *generated* multi-certificates are not
  viable and Option 3 must shift to consuming *hand-proved* certificates only.
- **Verdict: stage A is closed, and the kill criterion did not fire.** False rejection is
  4% author-written and 1-of-5 externally; both failures landed in *one* rule, and that rule
  was relaxable without touching soundness (stage 2k did it once already). The premise Stage
  C depends on — that generated multi-certificates are obtainable at a tolerable rate — is
  **supported by measurement rather than assumed.** The remaining known gaps (leaks
  uncovered; `b12`'s guard-validated bound; nested counted loops) are recorded, not
  scheduled: the corpus has told us what it can, and continuing to drive it to zero is the
  Option 1 path §4 rejects. **Next work is Stage B.**

### Stage B — One real artifact, one real certificate, one real composition. *(3–5 sessions)*

Pick **CN** as the first external producer (real C, active, POPL 2023/2025, runtime-testable
specs, built on a real C semantics).

1. Take two CN-verified C functions with ownership specs.
2. Model *what CN's certificate asserts* as an instance of `GradedAction`/`Bridge` — not
   re-verifying the C, but **receiving** the guarantee, exactly as `Bridge.ofKernel` and
   `Bridge.ofPTPChannel` receive Dobrushin and quantum-channel guarantees today.
3. Prove that composing the two receptions accumulates componentwise, and that the
   assumption ledger for the pair is the union of the two computed bases.

- **Milestone:** a machine-checked statement of the form *"CN certifies f, CN certifies g,
  therefore the composite carries both guarantees with trusted base = ledger(f) ∪
  ledger(g)"* — with a non-vacuity witness where the composite's base is **strictly
  smaller** than the fixed three-entry base of either.
- **Kill criterion:** if CN's guarantee cannot be stated as a graded action without
  inventing the very interaction term `pair_comp_cert` says does not exist, the algebra
  does not describe real certificates, and the asset is not an asset.
- **Done, first pass** (`conf-typing/ConfTyping/CNReceive.lean`, sources in
  `conf-typing/corpus/cn/SOURCES.md`): **the kill criterion did not fire.** CN's ownership
  clause states as a graded action with grade = footprint, `mul` = union, and `act_mul` =
  associativity of `∨` — no interaction term was needed or invented. The milestone
  sentence is `cn_comp_footprint` + `cn_comp_ledger`, both `rfl`; `modifiesOnly_comp`
  proves independently that the union is genuinely a modifies clause for `g ∘ f`, so the
  grade is the property rather than bookkeeping. Non-vacuity landed twice:
  `cn_untouched_outside` *derives* the CN tutorial's own framed postcondition (`qv_ == qv`)
  from the composed certificate, and `cn_base_strictly_smaller` exhibits a world where the
  **SMT backend is unsound** and the frame certificate still stands — the computed base is
  strictly smaller than the fixed three-entry base, and stays so under composition.
- **What the stage did *not* buy, and it matters.** The reception is an encoding **done by
  hand and unchecked against CN's implementation**: we do not prove `take RW<T>(p)` implies
  `ModifiesOnly f {p}`, because that is CN's soundness theorem over Cerberus's memory
  model. `CStore` is a total map, so provenance, lifetime and alignment are absent, and the
  functional postcondition is not modelled at all. **Stage B's milestone was about the
  composition law, and that is what it got.** Consuming a real machine-readable CN
  artifact is Stage D's milestone, and remains untouched — which is exactly where the
  "reduces to a manual encoding exercise" kill criterion lives.

### Stage C — Heterogeneous composition: the actual claim. *(5–8 sessions)*

Two *different* tools, two *different* properties, one composition.

1. Second producer: a speculative-constant-time certificate (Jasmin-style SCT) or a
   Rust-IFC certificate, whichever has the cleaner statable guarantee.
2. Compose a CN-certified component with an SCT-certified component.
3. Attack it: find the **interaction term**. The secure-compilation result says composing
   distinct properties gives roughly the *intersection*; our `pair_comp_cert` says
   accumulation is componentwise. Both cannot be the whole story. Where they disagree is
   the paper.

- **Milestone:** either (i) a theorem giving conditions under which heterogeneous
  certificate composition is **non-lossy**, with a counterexample showing it fails without
  them; or (ii) a counterexample showing it is *always* lossy, which retires
  `pair_comp_cert`'s scope claim. **Both outcomes are publishable and both are progress.**
- **Kill criterion:** none. This stage cannot fail, only inform — which is why it is the
  centre of the plan.
- **Done, first pass** (`conf-typing/ConfTyping/HeteroCompose.lean`): **outcome (i), and the
  disagreement resolved rather than adjudicated.** Both stories are right, on opposite sides
  of one hypothesis. `Bridge.pair`'s `hmap` — the two certificates are about the *same
  artifact* — is `rfl` within one tool and is **the entire problem** across two tools over
  different semantics, where it becomes a semantic reconciliation obligation the composition
  law neither performs nor mentions. `pair_comp_cert` is true and free; the admission ticket
  is what costs, and the literature's intersections are the price of that ticket.
  - **The counterexample** (`arch_reconciliation_insufficient`) rules out the obvious
    reconciliation: the bounds-check-bypass gadget agrees with its architectural
    counterpart **on the store under every schedule** (rollback is perfect) and keeps its
    CN footprint architecturally, yet touches memory outside that footprint transiently.
    State-level agreement does not transfer an ownership certificate.
  - **The sufficient condition** (`cn_reception_transfers`): store reconciliation *plus*
    trace inertness — `Speculate.lean`'s `spec_inert` at this altitude — discharges `hmap`
    and carries the footprint to every schedule.
  - **The free half, genuinely heterogeneous** (`hetero_bundle_laws`): a CN footprint
    accumulating by **union** beside an SCT-shaped public set accumulating by
    **intersection**, advanced by one `Bridge.comp`, componentwise.
- **Done, second pass** (`conf-typing/ConfTyping/JasminSCT.lean`, sources in
  `conf-typing/corpus/jasmin/SOURCES.md`): the second producer transcribed, and **reading it
  changed the result**. A Jasmin SCT level is a **pair** — one level for normal execution,
  one for misspeculating execution: `public` = ⟨L,L⟩, `transient` = ⟨L,H⟩, `secret` = ⟨H,H⟩.
  - **`transient` is precisely the first pass's finding, already named by the other tool.**
    A CN certificate carried into a speculative world is public normally and unconstrained
    under misspeculation — which is `transient`, and Jasmin's type system distinguishes it
    from `public` for exactly the reason `arch_reconciliation_insufficient` had to build a
    counterexample to expose. `bcb_footprint_is_transient` states it;
    `protected_footprint_is_public` is `#protect` performing the upgrade, i.e.
    `cn_reception_transfers`'s hypothesis discharged by the mechanism Jasmin ships.
  - The anchor is `fig3a` from the S&P 2023 paper's own test file — the guarded load whose
    *value* becomes the *address* of a second access. **The first pass had built that
    gadget abstractly before any Jasmin was read**, which is the strongest evidence
    available here that the seam was located rather than constructed.
  - Heterogeneity is now a fact about two real tools rather than a property of a witness
    built to have it: **CN's footprints union, Jasmin's levels join**
    (`cn_unions_jasmin_joins`), one `Bridge.comp`. `touchesOnly_imp_arch` earns the
    lattice's own well-formedness — nothing sits at ⟨H, L⟩.
- **What remains.** No `.jazz` file is parsed and no Jasmin output is consumed; both
  receptions are hand encodings, unchecked against their tools. That is the same gap named
  in `CNReceive.lean`, and closing it for *either* tool is Stage D's milestone, not Stage
  C's. The counterexample and the bundle also remain separate results.

### Stage D — Make it a tool for the composition, not for the language. *(ongoing)*

`certcheck` should stop being a checker for `UCmd` and become a **ledger combinator**:
input = certificates emitted by real tools; output = the accumulated guarantee and the
computed trusted base, with the Lean proof object behind it.

- **Milestone:** the tool consumes two real certificate files and emits a composite
  certificate + trusted base that a third party can re-check.
- **Kill criterion:** if no external tool emits a machine-readable certificate we can
  consume (rather than prose in a paper), this reduces to a manual encoding exercise and
  should be scoped as such rather than sold as a pipeline.
- **Done, first pass** (`conf-typing/ConfTyping/JasminCert.lean`, `certcompose`, evidence in
  `conf-typing/corpus/jasmin/EMISSION.md`). The criterion was an **empirical question about
  two real tools**, and it was answered by looking. **It half-fires.**
  - **Jasmin emits.** Its SCT checker prints an inferred signature per function, and the
    project diffs that text against a checked-in `accept.expected` in CI — output stable
    enough to parse, and a statement of *what was established*. Copied here verbatim;
    `certcompose` reads it, composes two certificates by the stage-C law, and prints the
    composite with its trusted base. `compose_lvl_is_sctLvlGA` proves the level it computes
    is exactly `sctLvlGA.mul`.
  - **CN does not.** Its JSON is a **timing log** (its own reader: "the JSON (ish) timing
    output", parser "a total hack"); its Coq export emits proof *obligations* plus a support
    library — work to discharge, not a guarantee to receive; success is an exit code and
    prose.
  - **So the scope is corrected, not smoothed over:** a pipeline for Jasmin, a hand encoding
    for CN. **A composite of two *different* tools still cannot be built from consumed
    artifacts alone** — a fact about what the ecosystem emits, not about the algebra. The
    milestone's "two real certificate files" is met within one tool and not across two.
  - **Coverage, measured: 20 of 57 (35%).** The other 37 emitted certificates are
    polymorphic or compound and have no image in `SLvl`; recorded as unreceived rather than
    flattened. The gap is in the receiving model, not in Jasmin.
  - `jasmin_base_strictly_smaller` gives the computed base for the second tool: a
    source-level claim does not need the compiler-preservation theorem, an assembly-level
    claim does, and `--assembly` is the difference in the printed trail.

### What happens to the existing work

- **Keep and maintain:** `transport-calculus` (the algebra), the ledger stages (1e, 2c,
  `LedgerBridge`), `transport-kernel` (five inhabited instance families — these are the
  evidence the interface is not vacuous).
- **Freeze, do not extend:** `UCmd`, `bcheck`, `Surface.lean`, `certcheck`-as-language-checker.
  They stay as the worked demonstration that a *generated* multi-certificate is possible at
  all, which is a genuine premise of Stage C. **No further stages that add rules to the toy
  language.**
- **The ω₁ line** is decoupled boundary mathematics and is unaffected by any of this.

---

## 6. What this plan does *not* claim

- It does not claim we will surpass Jasmin, CN, seL4 or Verasco on their own properties. We
  will not, and §2 is why.
- It does not claim the composition algebra is novel *as algebra* — graded monads and
  refinement composition are well-studied. The claim is narrower: *heterogeneous,
  per-artifact, machine-checked certificate accumulation with a computed trusted base*, and
  Stage C is designed to falsify even that.
- It does not assume the false-rejection number will be good. Stage A exists because it
  might be terrible, and that would be worth knowing in two sessions rather than twenty.
